# Research: Fix Ping — Full Code Path Synthesis

**Date**: 2026-04-06
**Git Commit**: `442a2f1`
**Branch**: main
**Repository**: pyro_fw

## Research Question

What code changes are needed to fix ping (`ping 192.168.7.1` from macOS), which has
been broken since commit `1116373` (DMA UART TX)?

---

## Summary

There are **two independent ping failure modes** at HEAD. Both have clear fixes.
The existing plan `thoughts/shared/plans/2026-04-06-fix-ping.md` covers them.

| Bug | When | Confirmed | Fix |
|-----|------|-----------|-----|
| **Bug A** (sleep/wake) | macOS sleep → wake, no replug | ✅ UART trace confirmed | Deferred `tud_network_ecm_resume()` from `tud_resume_cb()` |
| **Bug B** (fresh connect) | Physical replug w/ DMA UART TX | ❓ Hypothesis — Phase 1 test needed | Replace DMA UART TX with IRQ ring buffer |

The DMA-as-root-cause hypothesis for Bug B has not been ruled out — it is the
**only networking-relevant change** in the regression commit range. Phase 1 of the
plan (swap `hal_telemetry_send` to `uart_write_blocking`, test ping) is the
cheapest way to confirm or refute it.

## Detailed Findings

### 1. Why DHCP Works But ICMP Doesn't

DHCP and ICMP take fundamentally different code paths through the network stack:

**DHCP path** (`src/lwipopts.h:17`):
```c
#define LWIP_IP_ACCEPT_UDP_PORT(p)  ((p) == PP_NTOHS(67))
```
This macro intercepts DHCP at `ip4_input()` **before** destination IP checking and
before ARP resolution. `dhserver.c` constructs its own reply with raw Ethernet/UDP
headers and calls `linkoutput_fn()` directly. DHCP bypasses: ARP cache lookup,
`icmp_input()`, `ip4_output()`, and `etharp_output()`.

**ICMP path** (`src/lwipopts.h:10` — `LWIP_ICMP 1`):
The full lwIP stack:
```
tud_network_recv_cb() → received_frame = [ICMP pbuf]
net_service() → ethernet_input() → ip4_input() → icmp_input()
  → ip4_output() → ip4_output_fn() → etharp_output()
  → ARP cache lookup (must already contain host MAC)
  → linkoutput_fn() → tud_network_can_xmit() → tud_network_xmit()
```

ICMP fails if **any** of these steps fail: `received_frame` slot occupied when echo
arrives, ARP cache miss, `can_xmit == false` at reply time, or `linkoutput_fn()`
exhausting its 20 retries.

### 2. The `can_xmit` State Machine (ecm_rndis_device.c)

`can_xmit` is a `static bool` (`ecm_rndis_device.c:83`) that gates all USB IN
transfers:

| Event | `can_xmit` |
|-------|-----------|
| Startup (BSS) | `false` |
| `SET_INTERFACE alt=1` (patched handler, line 274) | `true` |
| `do_in_xfer()` — every USB IN transfer start (line 90) | `false` |
| `netd_xfer_cb()` IN complete, non-ZLP (line 371) | `true` |
| `netd_xfer_cb()` IN complete, ZLP case (lines 367–368) | `false` → then `true` after ZLP |
| `tud_network_ecm_resume()` (line 230) | `true` (force) |
| `tud_suspend_cb()` [no-op stub] | unchanged |
| `tud_resume_cb()` [no-op stub] | unchanged |

After macOS sleep/wake: `can_xmit` is unchanged (possibly still `false` from an
in-flight transfer interrupted by suspend). macOS's `IOUSBNetworkingFamily` also
stalls — it waits for a fresh `NETWORK_CONNECTION` CDC notification before resuming
routing. Neither happens without `tud_resume_cb()` calling `tud_network_ecm_resume()`.

### 3. `tud_network_recv_renew()` — Only Called When Frame Arrives

`net_service()` (`src/net_glue.c:177–185`):

```c
void net_service(void) {
    if (received_frame) {               // ONLY enters if a frame was received
        if (ethernet_input(received_frame, &netif_data) != ERR_OK)
            pbuf_free(received_frame);
        received_frame = NULL;
        tud_network_recv_renew();       // re-arms OUT endpoint
    }
    sys_check_timeouts();
}
```

After USB resume, if no frame has arrived (`received_frame == NULL`), the `if` block
is skipped entirely and `tud_network_recv_renew()` is **never called**. The OUT
endpoint stays un-armed indefinitely until a frame arrives. This creates a chicken-
and-egg situation: the OUT endpoint isn't re-armed until a frame comes in, but a
frame can't come in until the endpoint is re-armed.

`tud_network_ecm_resume()` breaks this deadlock by explicitly calling
`tud_network_recv_renew()` as part of its reset sequence.

### 4. DMA UART TX — What Changed in Commit 1116373

The DMA UART TX system itself is non-blocking and fast — `hal_telemetry_send()`
copies data to a ring buffer and kicks a DMA channel (`src/hal_hardware.c:408–426`).
No spin-loops. `uart_dma_irq()` is a 3-instruction ISR.

**The one behavioral change relevant to ping** is in `tud_network_init_cb()`
(`src/net_glue.c:126–132`), called by TinyUSB on every `SET_INTERFACE alt=1`:

| Version | `lwip_uart_printf()` implementation | Duration |
|---------|-------------------------------------|---------|
| v2.1.28 | `uart_write_blocking()` — blocks until all bytes sent | ~1.2 ms |
| HEAD (DMA) | `hal_telemetry_send()` — enqueue + DMA kick | ~5 µs |

The v2.1.28 blocking stall inside `tud_network_init_cb()` introduced ~1.2 ms of
delay before TinyUSB continued processing `SET_INTERFACE alt=1` (setting
`can_xmit = true` and calling `tud_network_recv_renew()`). Whether that timing
coincidence is load-bearing or coincidental cannot be determined by code analysis
alone — hence Phase 1 of the plan.

**DMA channel conflict is ruled out**: TinyUSB's RP2040 driver (`dcd_rp2040.c`) uses
only `USBCTRL_IRQ` and USB DPSRAM — zero system DMA channels. `dma_claim_unused_channel()`
in `uart_dma_init()` only touches user channels 0–11 and cannot interfere.

### 5. Single-Slot Receive Buffer Race

`tud_network_recv_cb()` (`src/net_glue.c:102–118`) uses one static slot:

```c
static struct pbuf *received_frame;   // net_glue.c:20

bool tud_network_recv_cb(const uint8_t *src, uint16_t size) {
    if (received_frame) {       // slot occupied — drop incoming frame
        net_rx_drop++;
        return false;           // tells TinyUSB: DO NOT re-arm OUT endpoint
    }
    // ... allocate pbuf, copy, store in received_frame ...
    return true;                // tells TinyUSB: re-arm OUT endpoint
}
```

When `return false`:
- TinyUSB does **not** auto-call `tud_network_recv_renew()`.
- The OUT endpoint is left un-armed.
- `net_service()` will call `tud_network_recv_renew()` on the **next** successful
  `ethernet_input()` cycle, re-arming the endpoint.
- Any frames the host sent while the endpoint was un-armed are silently lost.

Under normal steady-state operation, the main loop runs fast enough that this is
transient. But if `ethernet_input()` stalls (e.g., `linkoutput_fn()` calling
`tud_task()` 20 times on every TCP ack), the slot can stay occupied long enough to
drop the ARP request or ICMP echo that arrives next.

### 6. `linkoutput_fn()` Nested `tud_task()` Calls

`linkoutput_fn()` (`src/net_glue.c:61–77`) calls `tud_task()` up to 20 times while
waiting for `can_xmit` to become true. This call is nested inside `ethernet_input()`,
which is called from `net_service()`. Each `tud_task()` call inside the retry loop
can trigger `tud_network_recv_cb()` — if a second frame arrives while the first is
being processed, it's dropped.

At full-speed USB (1 ms frames), 20 `tud_task()` iterations spans at most ~20 ms of
USB events. For ICMP reply (typically a single non-ZLP packet), `can_xmit` should
be restored by `netd_xfer_cb()` within one USB frame (1 ms), so the retry loop
typically exits on the 2nd–3rd iteration.

### 7. Fix A: Sleep/Wake Recovery (Not Yet Implemented)

`src/net_glue.c` at HEAD has **no** `tud_suspend_cb`, `tud_resume_cb`,
`tud_mount_cb`, or `tud_umount_cb`. All four are TinyUSB weak no-op stubs.

The fix is to add to `src/net_glue.c`:

```c
static volatile bool ecm_resume_pending = false;

void tud_resume_cb(void) {
    ecm_resume_pending = true;   // defer — cannot call usbd_edpt_xfer from callback
}
```

And modify `net_service()`:

```c
void net_service(void) {
    if (ecm_resume_pending) {
        ecm_resume_pending = false;
        tud_network_ecm_resume();        // sets can_xmit=true, sends NETWORK_CONNECTION
        if (mdns_started) mdns_resp_restart(&netif_data);
    }
    if (received_frame) {
        if (ethernet_input(received_frame, &netif_data) != ERR_OK)
            pbuf_free(received_frame);
        received_frame = NULL;
        tud_network_recv_renew();
    }
    sys_check_timeouts();
}
```

`tud_network_ecm_resume()` is already defined in the patched
`~/.pico-sdk/sdk/2.2.0/lib/tinyusb/src/class/net/ecm_rndis_device.c:227–232`.

### 8. Fix B: DMA UART TX → IRQ Ring Buffer (Plan Phase 2)

The plan proposes restoring the v2.1.28 IRQ ring buffer from commit `8850072`.
Key differences:

| | DMA UART TX (HEAD) | IRQ Ring Buffer (v2.1.28) |
|-|-------------------|--------------------------|
| IRQ used | `DMA_IRQ_0` | `UART0_IRQ` |
| ISR duration | 3 instructions | drains PL011 FIFO (loop) |
| Buffer | 8 × 256-byte pool (2 KB) | 512-byte circular buffer |
| Main loop blocking | None | None |
| USB interaction | None (DPSRAM separate) | None |

The IRQ ring buffer is confirmed working with ping at v2.1.28.

## Ping Path (Normal Fresh Connect — Expected Working Sequence)

```
1. macOS: ARP request (broadcast)
   USB OUT → tud_network_recv_cb() → received_frame = [ARP pbuf]

2. net_service() → ethernet_input() → etharp_input()
   ├── ARP cache populated: 192.168.7.2 → hostMAC
   ├── ARP reply → linkoutput_fn() → can_xmit=true → tud_network_xmit()
   │   └── do_in_xfer() → can_xmit=false
   └── received_frame=NULL; tud_network_recv_renew()

3. netd_xfer_cb() → can_xmit=true

4. macOS: ICMP echo request
   USB OUT → tud_network_recv_cb() → received_frame = [ICMP pbuf]

5. net_service() → ethernet_input() → ip4_input() → icmp_input()
   ├── echo reply → ip4_output() → etharp_output()
   │   └── ARP cache hit → linkoutput_fn() → tud_network_xmit()
   │       └── do_in_xfer() → can_xmit=false
   └── received_frame=NULL; tud_network_recv_renew()

6. netd_xfer_cb() → can_xmit=true
7. macOS receives ICMP echo reply ✓
```

## Open Questions

1. **Does Phase 1 (blocking UART) fix fresh-connect ping?** This is the only way to
   confirm whether Bug B is real and DMA UART TX is the cause.

2. **Does macOS send `SET_ETHERNET_PACKET_FILTER` after receiving `NETWORK_CONNECTION`
   from `tud_network_ecm_resume()`?** If yes, `ecm_report(true)` fires twice — harmless
   but worth verifying.

3. **Does `received_frame != NULL` during the `ecm_resume_pending` handling in
   `net_service()`?** The proposed fix processes `ecm_resume_pending` before the
   `received_frame` check, which is safe — but if `ethernet_input()` triggers
   `linkoutput_fn()` which calls `tud_task()` and the resume-triggered NETWORK_CONNECTION
   IN transfer completes inside that nested `tud_task()`, the order of operations is
   benign (they're on separate endpoints).
