# Fix Ping Regression Implementation Plan

## Overview

Ping to 192.168.7.1 has been broken since commit `1116373` (DMA UART TX, v2-13).
DHCP works (macOS gets 192.168.7.2) but ICMP echo replies never arrive.
This plan isolates the root cause and restores ping.

## Current State Analysis

**What works:** USB enumeration, ECM link-up, DHCP lease assignment, HTTP.

**What's broken:** ICMP (ping). ARP may also silently fail, which would block
ping before any ICMP packet is ever sent.

**Commits since ping last worked (v2.1.28 = `8850072`):**
- `1116373` — DMA UART TX replaces IRQ-based ring buffer; removes `stdio_init_all()`
- `3d1491e` — LED heartbeat on GPIO 25 (trivial, not suspected)

**Working tree:** Only `VERSION` is modified. Net/USB code is at HEAD.

### Key Discoveries

- `src/hal_hardware.c:392–404` — `uart_dma_init()` calls
  `irq_set_exclusive_handler(DMA_IRQ_0, uart_dma_irq)` then
  `irq_set_enabled(DMA_IRQ_0, true)`. On RP2040 Cortex-M0+ all IRQs default
  to software priority 0. DMA_IRQ_0 (exception #27 = IRQ11) has lower exception
  number than USBCTRL_IRQ (exception #42 = IRQ26), so at equal software priority
  DMA_IRQ_0 wins ties and can preempt USBCTRL_IRQ.

- `src/hal_hardware.c:408–426` — `hal_telemetry_send()` has a TOCTOU race:
  `dma_channel_is_busy()` is checked, then `uart_dma_kick()` is called.
  Between the check and the kick, `uart_dma_irq` can fire, increment `tx_q_tail`,
  and call `uart_dma_kick()` itself. If the IRQ drains the last queued message
  between the check and the kick, `uart_dma_kick()` in the main loop sees
  an empty queue and does nothing — the newly enqueued message never starts.
  This is a soft stall (UART stops outputting) but not a hard network break.

- `src/net_glue.c:126–132` — `tud_network_init_cb()` calls `lwip_uart_printf()`
  which now calls `hal_telemetry_send()` (non-blocking DMA kick) instead of the
  v2.1.28 `uart_write_blocking()` (synchronous ~1.2 ms stall). The synchronous
  stall may have been providing timing slack that allowed USB host state machines
  to settle. This is speculative but worth noting.

- `ecm_rndis_device.c:262–285` — ECM activation path: after `SET_INTERFACE alt=1`,
  TinyUSB calls `tud_network_init_cb()`, sets `can_xmit = true`, calls
  `tud_network_recv_renew()`. ECM sends `NETWORK_CONNECTION` notification only
  after receiving `SET_ETHERNET_PACKET_FILTER` (line 297-300). This sequence is
  the same in both v2.1.28 and HEAD — not the regression.

- TinyUSB RP2040 driver (`dcd_rp2040.c`) uses **no system DMA channels** —
  only USBCTRL_IRQ. So there is no DMA channel conflict.

### What Was Ruled Out

- DMA channel conflict with TinyUSB: TinyUSB RP2040 uses no system DMA.
- `stdio_init_all()` removal: `pico_enable_stdio_uart/usb` are both 0 in
  CMakeLists.txt, so `stdio_init_all()` was a no-op in v2.1.28.
- LED heartbeat (`3d1491e`): GPIO toggle only, no USB interaction.
- ECM NETWORK_CONNECTION sequence: unchanged between versions.
- `linkoutput_fn` retry loop: same in both versions.

## Desired End State

`ping 192.168.7.1` from macOS succeeds immediately on device plug-in (within the
DHCP lease time, typically <5 s). Firmware retains DMA UART TX if possible, or
falls back to IRQ ring buffer.

## Phase 1: Isolate — Disable DMA UART TX and test

**Goal:** Confirm DMA UART TX is the root cause by making `hal_telemetry_send`
synchronous (blocking UART write), then testing ping. If ping works, the DMA
path is the culprit and we proceed to Phase 2.

### Changes Required

#### 1.1 Temporary: make `hal_telemetry_send` blocking

**File:** `src/hal_hardware.c`

Replace the `hal_telemetry_send` implementation body with a direct
`uart_write_blocking` call (keep the DMA init and structures to avoid
linker changes, but bypass DMA for the actual write):

```c
void hal_telemetry_send(const char *sentence) {
    if (!sentence) return;
    int n = (int)strlen(sentence);
    if (n <= 0) return;
    uart_write_blocking(uart0, (const uint8_t *)sentence, (size_t)n);
}
```

Leave `uart_dma_init()` in place (called from `hal_platform_init()`) but add a
comment that it is temporarily bypassed. This avoids disturbing the init sequence.

## Phase 2: Fix — Replace DMA UART TX with IRQ ring buffer

**Goal:** Restore the IRQ-based ring buffer from v2.1.28 (v2-10 code). This is
the known-working implementation. It removes DMA_IRQ_0 from the picture entirely.

The v2-10 ring buffer was:
- 512-byte circular buffer
- UART0 TX ISR drains ring into PL011 FIFO
- `hal_telemetry_send()` copies bytes into ring; re-arms TX interrupt

This approach is strictly better than reverting to `uart_write_blocking` because:
1. Non-blocking (like DMA), no stalls in main loop or callbacks
2. No DMA_IRQ_0 interaction with USB
3. Known working with USB ping

### Changes Required

#### 2.1 Restore IRQ ring buffer in `hal_hardware.c`

**File:** `src/hal_hardware.c`

Remove the DMA init code and restore the IRQ ring buffer from v2.1.28.
The diff restores these exact sections from commit `8850072`:

**Add** (verbatim from v2.1.28 / `8850072:src/hal_hardware.c`):
```c
/* ── UART TX ring buffer (v2-10) ──────────────────────────────────── */
#define UART_TX_BUF_SIZE 512
#define UART_TX_BUF_MASK (UART_TX_BUF_SIZE - 1)

static volatile uint8_t uart_tx_buf[UART_TX_BUF_SIZE];
static volatile int uart_tx_head = 0;
static volatile int uart_tx_tail = 0;

static void uart_tx_drain_isr(void) {
    while (uart_is_writable(uart0)) {
        int t = uart_tx_tail;
        if (t == uart_tx_head) break;
        uart_get_hw(uart0)->dr = uart_tx_buf[t];
        uart_tx_tail = (t + 1) & UART_TX_BUF_MASK;
    }
    if (uart_tx_tail == uart_tx_head)
        hw_clear_bits(&uart_get_hw(uart0)->imsc, UART_UARTIMSC_TXIM_BITS);
}

static void uart0_irq_handler(void) {
    if (uart_get_hw(uart0)->mis & UART_UARTMIS_TXMIS_BITS)
        uart_tx_drain_isr();
}

static void uart_tx_ring_init(void) {
    irq_set_exclusive_handler(UART0_IRQ, uart0_irq_handler);
    irq_set_enabled(UART0_IRQ, true);
    hw_clear_bits(&uart_get_hw(uart0)->imsc, UART_UARTIMSC_TXIM_BITS);
}

void hal_telemetry_send(const char *sentence) {
    if (!sentence) return;
    for (const char *p = sentence; *p; p++) {
        int next = (uart_tx_head + 1) & UART_TX_BUF_MASK;
        if (next == uart_tx_tail) break;  /* ring full — drop */
        uart_tx_buf[uart_tx_head] = (uint8_t)*p;
        uart_tx_head = next;
    }
    if (uart_tx_head != uart_tx_tail)
        hw_set_bits(&uart_get_hw(uart0)->imsc, UART_UARTIMSC_TXIM_BITS);
}
```

## Testing Strategy

### Why phase this at all?

Phase 1 (blocking UART test) is fast — 5 minutes to build/flash/test. It
definitively answers "is DMA UART TX the cause?" before investing in the Phase 2
rewrite. If Phase 1 shows ping still fails with blocking UART, the root cause is
elsewhere and Phase 2 would be wasted effort.

### If Phase 1 shows ping fails with blocking UART

Collect network diagnostic data by adding telemetry counters to `tud_network_recv_cb`
(frames received) and `linkoutput_fn` (tx_ok / tx_fail). Read these from the
`/status` HTTP endpoint or from UART output. This narrows down whether the failure
is at RX (frames not arriving), IP processing, or TX (can't transmit replies).

## Performance Considerations

The IRQ ring buffer approach has identical latency characteristics to DMA:
- Main loop: `hal_telemetry_send()` copies bytes into ring, re-arms ISR → no blocking
- ISR: drains ring into PL011 FIFO, fires on TX-FIFO-half-empty event
- The ring is 512 bytes vs DMA's 2 KB pool. At 115200 baud that's ~44 full
  telemetry sentences before any blocking. Same telemetry rates in practice.
