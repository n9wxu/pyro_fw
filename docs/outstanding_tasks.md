## How every task runs

Every task follows the same steps. No task closes any other way.

1. **Tests first.** Write the tests the task lists, and run them against the
   code as it stands.
   - Each must **fail**, except those marked *guard*.
   - A *guard* test protects behaviour the task must not change. It must pass
     before and after.
   - A new test that passes before the change proves nothing. Strengthen it
     until it fails.
2. **Change** the code, and the records in the same change:
   - `REQUIREMENTS.md`: requirements added, changed or removed;
   - `DECISIONS.md`: a DD entry for each design choice, numbered after the
     last;
   - `TRACEABILITY.md`: generated by `support/trace_matrix.py`;
   - `docs/flight_states.md`, where a state's behaviour changes.
3. **Pass.** Every test the task lists passes, and so does the gate.
4. **Commit and push.** The task is complete when its commit is pushed.

Everything is complete when CI passes on the last push.

## 4. Known limits of the flight software

Each is how the code behaves, measured. None is a defect against a
requirement. Say which to take up.

| ID | Limit | Measured |
|---|---|---|
| EST-2 | A sensor gap of more than 250 ms just before apogee delays apogee | up to 3.5 s on the host: the second of evidence starts again, the climb goes unseen, and so the fall must last 2 s (FLT-APO-07) |
| EST-3 | A run of wild readings is followed | half a second of readings 1500 hPa high, a second before apogee: the drogue 8.6 s after apogee, never before (DD-093) |
| EST-5 | `constacc` is late at height | no apogee within 2 s at 30 km from a cold pad and 45 km from a hot one; 7.7 s after a coast with no readings (`test/test_mach.c`'s report) |
| EST-7 | A reading a flash operation ran beside is used, noise and all (DD-106) | MK1B's MS5607 beside one: 8.5 to 17 Pa rms, 43 Pa at worst, against 2.3 Pa at rest. The host flights put 1.2 and 9 Pa on every reading and no disturbed one; that the filters absorb it is taken on trust. No MK1B on the bench with an MS5607 flies: both MK1B-8MBs carry BMP280s. A host flight with the measured disturbance on the readings each sync overlaps would test it |

## 8. Deferred, and not planned

### The MK1C bench fire (F1)

Deferred at your direction: "We will not do F1 anytime soon." The
firing path is done in code (DD-056) and tested against the board's plant
(`board_pyro_mk1c_tests`).

When it is taken up: a supervised fire with a 1 ohm pulse resistor on CN1 and
a scope on the firing bus, before any real match. Pass: `!PYRO FIRE` with
the bus at 90 % of the pack or more, the gate held no more than 40 ms,
`!PYRO F10 ch=1 still present` (a resistor does not open), and
`pyro1_fired` on `/api/status`. Then the same with a stopped loop (a
debugger halt mid-arm): U9 off within about 35 ms.

### False-launch reversion

Not scheduled, at your decision.

A board that declares a launch but is never armed, and whose altitude returns
to near the ground and stays there for several seconds, would go back to
PAD_IDLE. This is safe because the pyros are never armed before the arming
gate.

Such a board sits in ASCENT until it is restarted:
- its flight log stays open;
- the API stays live, so a reboot clears it (DD-058);
- the pad announcement has stopped;
- its ground reference is frozen.

If taken up, it needs:
- a requirement;
- a DD, because it is the only transition that leaves a flight state
  backwards;
- a decision on what happens to the open flight log;
- tests covering a glitch launch, a real slow launch that never arms, and a
  real flight.
